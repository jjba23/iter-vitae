# Vision

Iter Vitae turns one Guile Scheme file into a CV: a self-contained HTML page, an A4 PDF, and a plain-text resume for the systems that only accept a text box. The model is your persona, the view is a theme, and the whole thing is a file you can put in git and diff. This document is about the parts of that promise the code has not made good on yet — validation, translation coverage, and the awkward fact that a theme is not quite pluggable.

## Where iter-vitae is today

The render path is four small steps and has stayed small: `main.scm` parses the command line with `getopt-long`; `renderer.scm` loads your file as the module `(iter-vitae persona)` and reads each setting with `get-setting`, falling back to `(iter-vitae defaults)` for anything you did not define; the chosen theme turns that persona into SXML; `html.scm` serialises it to `index.html`, `text.scm` flattens the ATS body into `resume.txt`, and `pdf.scm` prints the page through headless Chromium.

Five themes ship: `ats` (one column, Arial 11pt, no tables, no icons, no external assets), `fatum`, `lapis` (fatum's calmer sibling, serif prose and mono labels), `ef-cyprus` (light, green accents) and `fundamental` (one sans-serif face, no network requests at all). `registry.scm` holds the single list that the renderer, the HTML dispatcher and `--all-themes` all read, so a theme is added in one place instead of three. `normalize-theme` falls back to `ef-cyprus` when the symbol is unknown, which is the right behaviour for a typo and the reason a mistyped theme is invisible.

The data model is the interesting part. Every piece of prose is a translation alist — `((en . "Software Engineer") (nl . "Softwareontwikkelaar"))` — and the key `all` wins over any locale, so a name or a product does not have to be repeated per language. `defaults.scm` carries the whole field set with commented examples: `display-name` and `job-title` are required, everything else is optional and renders as nothing when absent. `wizard.scm`, at 869 lines, is the other half of the model: `--init` asks the questions in plain language, `--locales en,nl,es` pre-answers the language question, each translatable question is asked once per language, pressing Enter reuses the first answer, and the result is reviewed before it is written.

The themes are deliberately unequal in ambition. `ef-cyprus.scm` is 712 lines, `fatum` 738, `lapis` 752, `fundamental` 488 and `ats` 499 — but the long ones are not better, they are decorated: `fatum`, `lapis` and `ef-cyprus` carry separate `-faces` modules for their typography, and all of them bundle the Olive stylesheet inline so the output stays one file. `fundamental` and `ats` are the two extremes and the two most opinionated: one deliberately has no dependencies at all, the other deliberately has no design.

Two releases are visible in the tree and not in the tag. `NEWS.org` has an unreleased section holding the wizard, `--format pdf`, `--all-themes`, `--all-locales`, optional portraits and the five-level proficiency scale, all of which are implemented in `src/`. The last tag is v1.5.1; the code is ahead of it.

The test surface is one spec per concern — `prelude`, `html`, `renderer`, `main`, `text`, `wizard` and `themes` — and the renderer and CLI specs run the program in a subprocess against a temporary destination, so they exercise argument parsing, file generation and escaping the way a user does. `populus/vega.scm` is the demo persona and `populus/joe.scm` is the author's own CV, which is the best kind of dogfooding: the tool's limitations show up on a real document with real dates.

Even the README's advertisement is reproducible. `scripts/generate-demo` renders the persona once per theme, captures each page in headless Chromium and composes the GIF, inside the pinned environment; the frames are screenshots of real output rather than mockups. For a document generator that is the right instinct, and it is the same instinct the suite is built on — show the artefact, not a picture of the intention.

The packaging is three recipes under `packaging/` — Arch, Debian and openSUSE — pinned to the same release as the sources, and none of the three archives ships the package yet. The launcher is POSIX `sh` and runs directly from a checkout, which is what makes "clone it and try it" a one-liner; `NEWS.org` records that this was once not true, and what the portability work cost.

The constraints that shape everything below: the persona is *loaded as a module*, so it is code and can compute anything — which means no schema can be enforced by a parser. Themes are functions from persona to SXML behind a `case` in `html.scm`, so a theme is data in one file and dispatch in another. And the ATS cleanup exists twice, once in `ats.scm` and once in `text.scm`, because one cleans HTML and the other builds plain text.

## The vision

1. **A persona is validated when it loads, and the error names the field.** Today a misspelt `jobs` renders a CV with no employment history and no warning; a `personal-contact` whose `emails` key is `email` renders nothing; a `languages` entry in the wrong shape produces an empty table row. Since the file is a Scheme module, the check has to happen after `load` and before the render: walk the expected shape, report every missing required field and every wrongly-shaped one by name, and refuse to write a document that would be quietly wrong. This is the largest gap in the project, and it is the gap a first-time user falls into.
2. **Translation coverage is a property of the persona, not a hope.** `--all-locales` renders every locale the persona defines, and nothing tells you that `nl` is missing three bullets, that the `all` key is silently covering a field you meant to translate, or that a `titles` override dropped the keys you did not restate. A render should be able to report, per locale, which fields fell back and which were absent — and the wizard's output should include every locale it was asked for by construction rather than by care.
3. **The output is verified for the reader it is written for.** An `ats` CV exists to be parsed by software that nobody can see, and a PDF exists to be printed on A4. In a few years both claims are tests: that the plain text uses conventional headings, one item per line, `-` bullets and no markup that a screener would choke on; that the HTML makes no network request and is a single file; that a modest CV fits one page in `ats` and that no theme leaves a heading orphaned at the foot of a sheet. Some of this exists as reasoning in `NEWS.org`; none of it exists as an assertion.
4. **A theme is a module you can drop in, not a `case` clause you have to patch.** The README's "write your own theme" instructions are honest and damning: copy `fundamental.scm`, rename the module, then edit `html.scm` in two places. In a few years the registry resolves a theme by module name, a conforming theme is one that exports two procedures, and a conformance spec runs against every bundled theme — so a third-party theme can be installed the way a package is.
5. **The persona is importable and exportable.** A CV written in one tool and trapped in that tool is a worse CV. JSON Resume is the nearest thing to an interchange format, and a persona that can be imported from and exported to it — lossy, and saying what it dropped — would make the choice of Iter Vitae a choice about authoring rather than a commitment about storage.

Statements 1 and 2 are about the model telling the truth; 3 and 5 are about the output being answerable to someone else; 4 is about the project being bigger than its author's taste. The first two are the ones a user feels immediately and the ones the code is furthest from: a persona with a typo currently produces a *plausible* document, and plausible is worse than broken, because it gets sent.

The shape of that validation is the design decision the rest of this document hangs on. `defaults.scm` is already the description of the model — it declares every field, gives each a default, and comments the shape of each — so a validator that read the same declaration rather than restating it would keep the two in step by construction. That is the interesting part: statement 1 is mostly a matter of *moving* information that already exists into a form a program can consume, which is the same move `version.scm` makes for the version.

## Features that are in scope and not built yet

Each of these is a seam the code has already cut.

- **Persona validation.** `defaults.scm` already declares the whole field set, and `get-setting` already knows the fallback. *The hard part* is that a persona is arbitrary Scheme — it can build `jobs` with a `map` over a data file — so the check must validate the *value* after evaluation, not the source, and must be able to say "this is computed and I cannot verify it" without crying wolf.
- **Locale coverage reporting.** `--all-locales` exists; the information to report on is already in hand at render time. *The hard part* is deciding what counts as a problem: a field covered by `all` is fine, a field covered by `all` that *looks* translatable is a question, and a `titles` override that drops a key is a trap the README warns about in prose.
- **A shared plain-text model.** `ats.scm` cleans HTML for screeners and `text.scm` builds plain text; both implement the same section order and the same conventions. *The hard part* is that the two are not the same job — one filters SXML, the other writes lines — so the shared piece is a description of what the ATS output must contain, not a shared function.
- **A corpus of real ATS output.** There is no record of what a screener actually reads. *The hard part* is that the software is invisible to the author by design: the only honest approach is a set of published parser behaviours, versioned, with a note about when each was last checked.
- **A print engine that is not a browser.** `--format pdf` drives headless Chromium, discovered portably and overridable with `ITER_VITAE_BROWSER`. *The hard part* is that a real typesetter is a project in itself, and the current arrangement is genuinely the pragmatic one; what is missing is a documented answer for a machine with no browser at all.
- **Portrait handling.** A local image is embedded as a data URI so the CV stays one file. *The hard part* is that the README already asks the user to resize to 400–600 px and stay under 200 KB — advice that a five-line resize in the program would make unnecessary, and that Guile has no comfortable image library for.
- **Inline HTML is trusted.** Most localised fields accept HTML, and `ats` strips tags and decodes entities. *The hard part* is that unbalanced markup in a bullet is currently a layout surprise rather than an error, and the fix has to tolerate the emphasis tags the README actually recommends.
- **The wizard's advanced step.** `--init` covers every content field and offers an optional step for renaming section headings. *The hard part* is that themes read different fields, so a wizard that is complete for one theme is not complete for another, and the honest version has to say which theme it is writing for.
- **Destination safety.** `--destination` is deleted and recreated on every run, and the README warns in a block quote. *The hard part* is that the warning is the whole mechanism: there is no guard against pointing it at a directory that holds something else, and a prompt would break the scripted use.
- **The proficiency scale beyond three languages.** `language-proficiency-label` is shared by every renderer and ships English, Dutch and Spanish labels. *The hard part* is that the five-level scale is a convention with national variations, so a fourth language needs a translator's judgement about the labels rather than a string swap.

## New features that would be worth having

- **`iter-vitae --check`.** Validate the persona, list the locales it defines, report fields that fall back, warn about an unwritable `--destination`, and exit non-zero — writing nothing. The destination being deleted and recreated on every run is the one genuinely destructive behaviour in the program, and a dry run is the obvious complement to it.
- **Dates that compute themselves.** `time` is free text today, with `=>` displayed as an en dash. A persona that records a start date and an optional end date could render "2020 — present", compute the duration, and let the theme decide whether to show it — which turns one of the most-retyped parts of a CV into arithmetic.
- **A cover letter that shares the persona.** The name, the contact block, the employer history and the locale are all already there; a letter is a second template and a few extra fields, not a second model. *(Speculative — a letter has a different structure and a different reader, and the temptation to make it a theme of the CV is probably wrong.)*
- **A `--watch` mode.** Re-render into `--destination` whenever the persona changes, so a browser tab reloaded by hand is a live preview. *Why it is cheap:* `maak dev` already hot-reloads the example persona, so the mechanism is a small version of an existing task; the missing part is doing it without a build system.
- **`--format json-resume`, and the import beside it.** Export what maps, list what did not, and accept a partial import that fills a persona skeleton. *(Speculative in scope: the mapping is lossier than it looks, because JSON Resume has no notion of a translation alist.)*
- **A theme gallery built by the project.** `--all-themes` already renders every theme; the README's demo is a GIF assembled by `scripts/generate-demo`. A generated page showing the same persona in every theme, at print size, would be the honest advertisement. *(Speculative in form; the demo script is already most of it.)*
- **An accessibility and print audit of the HTML output.** `lang` is declared, links open safely, the `ats` theme is deliberately plain — and nothing checks the rendered page for heading order, contrast, or the page-break rules the print styles claim. *(Speculative: it needs a browser in CI, which the project has for `--format pdf` already.)*
- **A theme that renders to plain text only.** The `ats` mode is a theme *and* a format, and the two are not quite the same thing: `--format text` ignores the theme entirely. A text theme — a way to describe the plain-text layout the way `fundamental` describes the HTML one — would collapse the duplicated cleanup and let somebody write a plain-text CV that is actually pleasant to read. *(Speculative, and the smallest version of it may be "one more function in `text.scm`".)*
- **A `--since` mode for a targeted application.** A CV written for a specific posting is a branch, and the README already suggests branching in git. A mode that renders only the sections that differ from the base persona would make the branch's diff visible as a document. *(Speculative; the value depends on how much tailoring people actually do, which nobody has measured.)*

The pattern worth noticing is that most of these reduce to "make the model say what it knows". A persona knows its locales, its fields and its dates; a theme knows which fields it reads; a render knows which values fell back. Almost everything missing is a way to ask.

## Contributions that would move the needle

1. **Persona validation with named errors.** One function, called after `load`, before any theme runs. *Why it is a good task:* it converts the project's most common failure — a CV that renders but is missing a section — from silence into a message, and `defaults.scm` already holds every fact it needs.
2. **A fourth theme that is not a variation.** `fatum`, `lapis` and `ef-cyprus` are siblings; `fundamental` and `ats` are the two extremes. A theme from a different design tradition would test whether the theme contract is real or whether it merely tolerates the author's taste. *Why it is a good task:* it is the fastest way to discover what a theme actually needs from the model, and the answer is what statement 4 depends on.
3. **One print assertion.** A spec that renders `populus/vega.scm` to `ats` PDF, counts the pages with a PDF reader, and asserts it is one. *Why it is a good task:* the README claims a modest CV fits one A4 page in `ats`, and a claim like that should fail a test rather than be rediscovered.
4. **A locale-coverage report.** Print, per locale, which fields fell back to `all` and which were absent. *Why it is a good task:* it needs no new machinery, it makes `--all-locales` honest, and it is the kind of output that teaches a user about their own persona.
5. **A translation of the wizard and the theme labels.** The five-level proficiency scale ships English, Dutch and Spanish labels; a fourth language is a table entry and a `.po`-shaped gap to fill. *Why it is a good task:* small, well-bounded, and immediately useful to somebody who does not write English.
6. **The `html.scm` `case` retirement.** Replace the theme dispatch with a resolution that a third party can extend, and add the conformance spec that proves it. *Why it is ranked last:* it is a public-API decision on a project that has just declared a stable one, and it should be made deliberately rather than as a drive-by.
7. **A persona field that is missing from every theme.** Take one field — `driver-licenses` or `interests-hobbies`, both of which are optional and skipped when empty — and make it render in all five themes with a spec each. *Why it is a good task:* it is small and it exposes the real cost of a theme, which is not the layout but the four places a new field has to be remembered.
8. **The `--help` text and `resources/help.txt`.** They are shipped together and are the first thing anybody reads. *Why it is a good task:* an hour, and a wrong flag in the help text is a bug report nobody files.
9. **A fourth language in the wizard and the labels.** Every question, the five proficiency labels and the section headings are translatable, and the wizard currently speaks three languages. *Why it is a good task:* it is the contribution that makes the multilingual model real for somebody else, and it needs no Scheme beyond one table.

The ranking is value per hour, not importance. Item 1 is an afternoon and removes the failure that makes people give up; item 2 is a day and produces knowledge nobody has; item 6 is the one that changes the project's shape and is deliberately last, because the first five make it safer. What is not on the list is another variation of the existing themes: three of the five are already siblings, and a sixth sibling would tell you nothing about whether the contract works.

## Compared to related projects

| Project | What it is | Where iter-vitae differs |
|---|---|---|
| JSON Resume | A JSON schema for CVs, with a theme ecosystem and a CLI around it | The nearest thing to an interchange standard, and a data format rather than a program. Iter Vitae has no schema to conform to and no lock-in to offer, which is exactly the trade statement 5 wants to close. |
| Reactive Resume | A self-hostable web application for building CVs in a browser | A client-side application with accounts, a database and a print stylesheet. Iter Vitae is a local program whose output is a file, and its source of truth is one text file in git rather than a row in a service. |
| RenderCV | YAML in, LaTeX-quality PDF out, aimed at academics | The closest philosophical cousin: one source file, version-controlled, several themes, real PDF. It is YAML and TeX; Iter Vitae is Scheme and HTML, which buys computation and multilingual alists at the cost of TeX's typography. |
| moderncv and Awesome-CV | LaTeX classes for a CV | Beautiful, and a TeX distribution away from being usable by a person who does not write TeX. Iter Vitae's `fundamental` theme is the deliberate answer: one face, no dependencies, opens from disk. |
| Typst CV templates | Modern typesetting with a friendlier language and fast PDF output | Typst is a better typesetter than a browser will ever be, and its templates are files you edit. What they do not have is a persona model, a wizard or (in most cases) an ATS mode. |
| Pandoc | A universal document converter with templates | Pandoc can produce a CV from Markdown with a template, and it will not validate your fields, emit a screener-safe plain text variant, or render five themes of the same data. |
| `resume-cli` and the JSON Resume themes | A Node CLI that renders a JSON Resume through a theme | The same shape of tool in a different ecosystem: a file renders through a theme. Its model is a schema, its themes are JavaScript, and its multilingual story is an `languages` array rather than a translation alist. |
| Hugo and Jekyll CV themes | Static site themes for a personal site | They publish a page; they do not produce a PDF, a plain-text resume, or a document in four languages from one source. |
| LibreOffice Write and Microsoft Word | The word processors most CVs are actually made in | Immediate beyond comparison, and a document you cannot diff, cannot branch for an application, and cannot render in three languages from one source. Also the only one of these that wins on print typography outright. |

What the others do that iter-vitae could still add: JSON Resume's schema is the thing that makes its ecosystem possible, and Iter Vitae's answer — validate the evaluated value rather than the source — is a harder version of the same idea that nobody has written yet. RenderCV and Typst both beat a browser at print typography, and a genuinely good `--format pdf` is a real argument the project currently concedes. Reactive Resume's live preview is the one place a browser application has an advantage that a CLI cannot match, and a `--watch` mode that re-renders into an open tab is the cheap version of it.

The ATS comparison deserves its own paragraph, because it is the claim easiest to make and hardest to keep. Every tool that emits "ATS-friendly" output is asserting something about software its author cannot run: which parser, which version, which quirks. Iter Vitae's `ats` theme is honest about being a set of conventions — one column, conventional headings, no tables, no images, no icons — and the only way that claim can become more than a convention is a corpus of real outputs and a way of noticing when one of them stops being parseable. That is a testable thing, it is not built, and it is the single most valuable open problem in this project.

Where iter-vitae is ahead and should stay ahead: multilingual content is the model rather than a feature, so every field is translatable and `--all-locales` is one flag; the ATS mode is a first-class theme with its own conventions, not a stylesheet tweak; the wizard means the tool is usable by somebody who does not write Scheme; and the output is one self-contained file with no network request, which is the only way a CV stays openable in ten years.

The one comparison that cannot go in the table is with a word processor, because that is what most people actually use. LibreOffice and Word win on immediacy and lose on everything this project cares about: the file is a binary blob, the diff is meaningless, the styles drift, and the same CV in three languages is three documents maintained by hand. The README's manifesto argues this at length and is right; what it does not say is that the word processor also wins on *print typography*, and that is the one ground the project has conceded rather than contested.

## In the long run

The long bet is that a CV should be a document you own and can rebuild, in the same sense that a piece of software is. Forty years of career means forty years of edits, and the tools that survive that span are the ones whose source is text and whose renderer is replaceable. Everything above — the validation, the coverage report, the conformance suite, the interchange format — is in service of the file still being renderable in 2066 by something that is not this program.

That is a stronger claim than it first sounds, and it has a consequence the project should keep in view: the persona format matters more than the renderer. A theme can be rewritten in a weekend; a data model that people have committed their career history to cannot be. Which means the modest, unglamorous work — naming a field, documenting its shape, refusing to silently accept a typo — is the work that decides whether the forty-year claim is credible.

The second bet is that the ATS mode is the most valuable thing in the project. Nobody enjoys writing for a screening algorithm, and everybody's application is read by one. A tool that produces the honest plain-text version, and tells you what it could not express, is doing something no LaTeX template and no web CV builder does.

The third bet is smaller and more personal: that the person who wrote this wanted a CV that lives in git, and that the wizard is the bridge for everyone who does not. The two halves have to keep pulling in opposite directions — the Lisp user wants `map` over a list of talks, the non-programmer wants questions — and the way that tension resolves is by keeping the *output* identical and the *input* optional.

What would falsify these bets is worth stating. If applicant tracking systems converge on parsing structured data rather than text, the `ats` theme becomes a compatibility shim rather than a feature, and the plain-text output stops mattering. If JSON Resume or its successor becomes the format everyone exports, then statement 5 stops being a nice idea and becomes table stakes. And if CVs themselves become generated profiles maintained by a platform, then forty years of edits is not a document problem at all — which would make this project a very well-made answer to a question that stopped being asked.

## How to read this document

The sections above are an argument about direction, not a backlog. The in-scope list names things the code has already half-built; the rest are proposals, and the speculative ones are marked. `NEWS.org` remains the record of what changed and when, and the changelog is the only place a promise is made.

A reader who knows the project can use the five statements as a filter. Does a change make the model louder about what it does not have, make the output answerable to a reader the author cannot see, or make a theme something somebody else can write? If it does none of those, it can still be worth doing — a nicer footer is a nicer footer — but it is not what this document argues for.

*This document describes intent, not commitments; the themes, the wizard and the suite remain the only account of what Iter Vitae does.*
