Iter Vitae is a free software project that aims to make it easy and maintainable to generate an attractive, modern and customizable /Curriculum Vitae/ or /resume/ for yourself and to allow you to define the course of your life and career directly in Guile Scheme code.

* The Manifesto
:PROPERTIES:
:CUSTOM_ID: the-manifesto
:END:

Everyone has the right to create a professional-looking Curriculum Vitae, using free software, without the constraints of proprietary software, lengthy setup processes, or a lack of freedom to modify layouts.

Traditional word processors like LibreOffice or similar can be cumbersome when trying to create a custom CV.

Iter Vitae offers an alternative by embracing the spirit of hacking and freedom, enabling you to customize every aspect of your CV.

With this tool, you can define the content, layout, and presentation of your CV directly in code, making it highly flexible and maintainable.

The tool separates data from its presentation (following the principles of the Model-View-Controller or MVC architecture), so you can focus on the data itself without worrying about formatting or styling.


** Build a Curriculum Vitae for your next 40 years
:PROPERTIES:
:CUSTOM_ID: build-a-curriculum-vitae-for-your-next-40-years
:END:

This tool isn't just about creating a one-off CV — it's designed for long-term use, so you can update and evolve your resume over the years. The software supports multilingual content and is fully extensible, allowing you to add new data entries, customize the design, etc.

Also, version-control your CV code, and enjoy all the benefits. Work with a sane and flexible multi-lingual compatible data model.

Remember that with Guile Scheme, and the Lisp super-powers, everything is extensible, hackable and modifiable at any moment, giving you ultimate control and power.

*** ats
:PROPERTIES:
:CUSTOM_ID: ats
:END:

An Applicant Tracking System first theme, designed for American job applications and automated resume screeners. It uses one column, Arial at a normal 11pt body size, plain block elements, selectable contact text, and the conventional headings recruiters and parsers expect: *Professional Summary*, *Skills*, *Work Experience*, *Education*, *Languages* and *Additional Information*.

There are no tables, images, icon fonts, web fonts, headers, footers or external assets. Inline HTML in persona fields is stripped so parsers receive plain text, and work and education entries are ordinary headings with bullet lists. The page prints cleanly to US Letter paper, so it can be exported to a text-based PDF from the browser.

#+begin_src scheme
(define document-theme 'ats)
#+end_src

ATS vendors configure parsing and ranking differently, so no theme can guarantee a pass. This theme removes the formatting causes of failed parses; still tailor the keywords to each posting, keep dates consistent, spell out acronyms once, and follow the employer's file-format instructions. Use the ~skills~ field to list the terms a posting asks for.

* Testing
:PROPERTIES:
:CUSTOM_ID: testing
:END:

The test suite uses [[https://codeberg.org/jjba23/veritas][Veritas]], the Guile testing framework that is already part of the development environment defined by ~manifest.scm~.  Tests live beside the source, under ~test/veritas/unit/~, and are discovered automatically by the Veritas runner.

The simplest way to run everything is through Maak:

#+begin_src shell
maak test
#+end_src

Or invoke the runner directly from a Guix shell:

#+begin_src shell
VERITAS_TEST_TYPE=unit \
    guix shell -m manifest.scm -- \
    guile --fresh-auto-compile -L ./src -L ./test \
    -c '((@ (veritas runner) run-tests))'
#+end_src

The suite covers the pure helpers in ~(iter-vitae prelude)~, the SXML serializer, every bundled theme, the renderer and the command-line entrypoint.  Renderer and CLI tests run the program in a subprocess against a temporary destination, so they exercise argument parsing, file generation and escaping exactly as a user would.

Useful Veritas environment variables while iterating:

- ~VERITAS_ONLY_SUITE="renderer"~ runs one suite.
- ~VERITAS_ONLY_TEST="spaces"~ runs matching test cases only.
- ~VERITAS_ONLY_FAILED=true~ reruns the cases that failed last time.
- ~VERITAS_SEED=<seed>~ replays the order printed by a shuffled run.

* Ways to install
:PROPERTIES:
:CUSTOM_ID: ways-to-install
:END:

/Four routes to the same 1.0.2, from the most automated to the most manual.  They all build the tag this README documents./

** From the Guix channel
:PROPERTIES:
:CUSTOM_ID: from-the-guix-channel
:END:
*GNU Guix* is the functional package manager this project is developed with: a build is a pure function of its inputs, so the same recipe gives the same result everywhere, and an upgrade that goes wrong can be rolled back.

The jointhefreeworld channel carries ~iter-vitae~ at 1.0.2, so a checkout of the channel is enough — no package definition to write:

#+begin_src shell
git clone https://codeberg.org/jjba23/guix-jointhefreeworld.git
guix install -L ./guix-jointhefreeworld iter-vitae
#+end_src

Add the channel to ~$HOME/.config/guix/channels.scm~ (the channel's README has the four lines) and a plain ~guix install iter-vitae~ keeps working on every later ~guix pull~.

** From the Nix flake
:PROPERTIES:
:CUSTOM_ID: from-the-nix-flake
:END:
*Nix* offers the same declarative, reproducible model with its own language, its own store and a binary cache, and it is a natural fit if the rest of your machine is already described in Nix.

The jointhefreeworld flake builds this project with this repository's own expression, so the package cannot drift from the source:

#+begin_src shell
nix build github:jjba23/nix-jointhefreeworld#iter-vitae
#+end_src

The same attribute is available as an overlay, so ~pkgs.jointhefreeworld.iter-vitae~ works inside a NixOS or home-manager configuration too.

** As a container image
:PROPERTIES:
:CUSTOM_ID: as-a-container-image
:END:
*Podman or Docker* is the route that puts nothing on the host: the ~Dockerfile~ in this repository builds the project in a builder stage and copies only what it installed into a runtime stage, so the image is small and the host keeps its own toolchain untouched.

#+begin_src shell
podman build -t iter-vitae .   # docker build -t iter-vitae . also works
podman run --rm -it iter-vitae
#+end_src

The image's entry point is Guile, with iter-vitae on its load path, which makes it useful for a quick try and for reproducing a bug on a clean system.

** As a distribution package
:PROPERTIES:
:CUSTOM_ID: as-a-distribution-package
:END:
*Debian, openSUSE and Arch* each get the project through their own package manager.  Packaging lives in this repository under ~packaging/~ and is pinned to the same release tag, so the recipes and the sources they build are versioned together.

None of the three archives ships iter-vitae yet, so these are recipes to build rather than packages to install from a mirror:

| Distribution   | Package      | How to build it                                                                     |
|----------------+--------------+-------------------------------------------------------------------------------------|
| Debian, Ubuntu | ~iter-vitae~ | copy ~packaging/debian~ to the repository root, then ~dpkg-buildpackage -us -uc -b~ |
| openSUSE       | ~iter-vitae~ | ~osc build~ with ~packaging/opensuse~                                               |
| Arch           | ~iter-vitae~ | ~makepkg -si~ in ~packaging/arch~                                                   |

Each recipe carries its own dependency list, so a missing library fails the build with its name rather than producing a package that cannot load.

** Which one?
:PROPERTIES:
:CUSTOM_ID: which-one
:END:
- *Guix* if you want the toolchain the project is tested with, and the ability to roll back a bad upgrade.
- *Nix* if the rest of your machine is already declarative; the flake pins nixpkgs and gives you a binary cache.
- *Container* if you only want to try the release, or reproduce a report on a machine that has nothing installed.
- *Distribution package* if you want the project managed by the same tool as the rest of your system, with its licence, manual page and launcher in the usual places.

** On Guix
:PROPERTIES:
:CUSTOM_ID: on-guix
:END:

Iter Vitae is officially distributed via the Guix package manager as ~iter-vitae~. You can alternatively choose to download it from source, useful for developing it or customizing it.
In that case you'll need:

- *Guix*: The Guix package manager will ensure a reproducible working software, and will manage all needed dependencies for you.
-  *Guile Scheme:*  This entire program is written using the official GNU extension language, Guile Scheme.
- Any web browser of your choice (ideally which can also print to PDF)

Check the ~maak.scm~,  and the ~guix.scm~ and  ~manifest.scm~ for more details.

For example, to enter an environment shell with mutastructura temporarily you can use:
#+begin_src shell
guix time-machine --channels=channels.scm -- shell -f guix.scm
#+end_src

You can also chain commands to it:
#+begin_src shell
guix time-machine --channels=channels.scm -- \
     shell -f guix.scm -- iter-vitae --help
#+end_src

In order to view the output this tool generates, we recommend you use a free web browser such as GNU IceCat or Firefox, and after running the tool, open the file at ~./dist/index.html~ or alternately upload and serve it from the web server of your choice. With ~--format text~, open ~./dist/resume.txt~ instead.

iter-vitae offers a ~--help~ / ~-h~ flag which will explain all options (also visible in ~resources/help.txt~). You should point iter-vitae to the path to  your configuration file:

#+begin_src shell
iter-vitae --locale nl --file /home/me/documents/my-cv.scm --destination /home/me/documents/dist
#+end_src

** Plain-text output
:PROPERTIES:
:CUSTOM_ID: plain-text-output
:END:

By default Iter Vitae writes ~index.html~. Some employers only accept plain-text uploads, so ~--format text~ writes ~resume.txt~ instead:

#+begin_src shell
iter-vitae --format text --file /home/me/documents/my-cv.scm --destination /home/me/documents/dist
#+end_src

The text renderer ignores the visual ~document-theme~ because plain text has no styling. It uses the same ATS-friendly section order and the same cleanup as the ~ats~ theme: conventional headings, one item per line, ~-~ bullets, visible contact details, and no HTML tags, entities, emoji or smart punctuation. Use it for text-only application forms; use the HTML output when a browser preview or PDF export is wanted.

* How to write your CV in Lisp?
:PROPERTIES:
:CUSTOM_ID: how-to-write-your-cv-in-lisp
:END:

Here follows an explanation of all the fields and possibilities that ~iter-vitae~ provides you.

Iter Vitae gives you the power of Lisp to define your CV. That means we mostly work with idiomatic data structures, specially ~list~ and ~alist~ (association lists). Some of those alists contain language-specific content, and as such, we call them ~translation-alist~, e.g.

#+begin_src scheme
`((en . "Software Engineer ⚙️")
  (nl . "Software Engineer ⚙️")
  (es . "Ingeniero de Software ⚙️"))
#+end_src

translation-alists can contain endless amount of translations for every language code that you want to support. If the value should be the same for all languages, simply use the key ~all~, e.g.

#+begin_src scheme
`((all . "Software Engineer ⚙️"))
#+end_src

Some variables have sensible defaults, and as such can be skipped from customization.
You should also look at the defaults for more info: [[file:src/iter-vitae/defaults.scm]]

Bear in mind that some themes might require additional variables that are not in other themes.

Also, for a "real-world" example, you can see my own CV: [[file:populus/joe.scm]]

HTML is directly supported in most localized fields, for example:
#+begin_src scheme
(en . "Architected and delivered a high-performance, real-time energy calculation service (<em class=\"italic\">“greenest moment of the day”</em>).")
#+end_src

The ~ats~ theme is the exception: it strips HTML tags and decodes entities so automated parsers only see plain text.

The following variables are read by Iter Vitae to construct a CV:

- ~titles~ is a list of ~translation-alist~ with content for each section's header, in different languages.
- ~document-theme~ is a symbol (e.g., ~'ef-cyprus~, ~'fatum~, ~'fundamental~ or ~'ats~) that specifies the visual theme, color scheme, or styling to be applied when the document is ultimately generated. See supported themes section above.
- ~display-name~ is a *required* ~translation-alist~ that represents the person's name.
- ~job-title~ is a *required* ~translation-alist~ that represents the job title to be displayed.
- ~job-title-link~ is an optional ~translation-alist~ that represents the URL to visit when clicking the job title header.
- ~personal-contact~ is an ~alist~ that expects the person's e-mail in the ~emails~ field, and the person's phone number in the ~phone-numbers~ field
- ~personal-links~ is an ~alist~ of optional fields that can contain ~blog~ , ~code~ and ~linked-in~ , all of which are strings.
- ~address-lines~ is a ~list~ of ~translation-alist~ and allows one to display address details, line-by-line.
- ~driver-licenses~ is an optional ~list~ of ~translation-alist~ that outlines your driving qualifications.
- ~interests-hobbies~ is an optional ~list~ of ~translation-alist~ used to describe your hobbies and personal interests.
- ~language-proficiency~ is an ~alist~ that defines the grading scale for your language skills. It maps a language code (like ~en~ or ~nl~) to an ~alist~ of integer levels (e.g., 1 to 4) alongside their localized string descriptions (e.g. ~"Elementary Proficiency"~ , ~"Native"~).
- ~languages~ is an ~alist~ detailing the languages you actually speak. Each key is a language code mapped to an ~alist~ containing a ~name~ (a ~translation-alist~ with the language's display name and optional emoji) and a ~proficiency~ field. The ~proficiency~ field is itself an ~alist~ mapping ~reading~, ~speaking~, and ~writing~ to the integer levels you defined in ~language-proficiency~.
- ~education~ is a ~list~ of ~alist~ data structures detailing your academic background, courses, and educational internships. Each entry expects ~name~ (the institution), ~location~, ~position~ (the degree or course name), ~time~, and ~experience~ (a ~list~ of ~translation-alist~ outlining what you learned or achieved).
- ~short-intro~ is a ~list~ of ~translation-alist~ that acts as your personal summary, biography, or cover letter excerpt.
- ~skills~ is an optional ~list~ of ~translation-alist~ naming the skills and tools you want a scanner to find. The ~ats~ theme renders them as one comma-separated line, while other themes currently ignore this field. For example: ~(((all . "Scala")) ((all . "Kubernetes")) ((all . "PostgreSQL")))~.
- ~jobs~ is a ~list~ of ~alist~ data structures detailing your professional experience. Each entry expects ~name~ (the institution), ~location~, ~position~ (the degree or course name), ~time~, and ~experience~ (a ~list~ of ~translation-alist~ outlining what you did or achieved).

* On Reproducibility: Why GNU Guix?
:PROPERTIES:
:CUSTOM_ID: on-reproducibility-why-gnu-guix
:END:

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
